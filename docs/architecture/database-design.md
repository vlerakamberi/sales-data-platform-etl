# Database design

## Scope and conventions

This document records the approved Repository 1 Milestone 2 database
architecture and final physical contract. It covers nine entities:
`sales_channels`, `stores`, `customers`, `product_categories`, `products`,
`orders`, `order_items`, `payments`, and `returns`.

The physical conventions are:

- surrogate primary keys use `BIGINT GENERATED BY DEFAULT AS IDENTITY`;
- monetary values use `NUMERIC(18,2)`;
- business-event timestamps use `TIMESTAMPTZ`;
- transactional and product currency codes use `CHAR(3)` and must contain
  three uppercase letters;
- country codes use `CHAR(2)` and must contain two uppercase letters;
- business columns have no defaults; identity generation is the only default;
- business relationships do not use `ON DELETE CASCADE`.

Business-event timestamps use `TIMESTAMPTZ` and represent the actual business
instant at which the corresponding event occurred. Timezone-aware source values
preserve that instant, with Repository 1 operational handling normalized to
UTC. These timestamps are distinct from ingestion or database-insertion time
and do not use `DEFAULT CURRENT_TIMESTAMP`.

## Relationships and cardinalities

- One `sales_channels` row relates to zero or many `orders`; every order has
  exactly one sales channel.
- One `stores` row relates to zero or many `orders`; an order has zero or one
  store because e-commerce orders may have no store.
- One `customers` row relates to zero or many `orders`; an order has zero or one
  customer because anonymous transactions are permitted.
- One `product_categories` row relates to zero or many `products`; every product
  has exactly one category.
- One `orders` row relates to one or many `order_items`; every order item has
  exactly one order.
- One `products` row relates to zero or many `order_items`; every order item has
  exactly one product.
- One `orders` row relates to zero or many `payments`; every payment has exactly
  one order.
- One `order_items` row relates to zero or many `returns`; every return has
  exactly one order item.

## Physical contract

### `sales_channels`

Stores the controlled set of channels through which orders are placed.

| Column | Type | Nullability | Key and constraints |
| --- | --- | --- | --- |
| `sales_channel_id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `NOT NULL` | Primary key |
| `sales_channel_code` | `VARCHAR(32)` | `NOT NULL` | Unique; non-blank |
| `sales_channel_name` | `VARCHAR(100)` | `NOT NULL` | Non-blank |

### `stores`

Identifies physical retail locations that may be associated with orders.

| Column | Type | Nullability | Key and constraints |
| --- | --- | --- | --- |
| `store_id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `NOT NULL` | Primary key |
| `store_code` | `VARCHAR(50)` | `NOT NULL` | Unique; non-blank |
| `store_name` | `VARCHAR(200)` | `NOT NULL` | Non-blank |
| `country_code` | `CHAR(2)` | `NOT NULL` | Structurally two uppercase letters |

### `customers`

Provides only the approved customer identity needed to associate a known
customer with an order.

| Column | Type | Nullability | Key and constraints |
| --- | --- | --- | --- |
| `customer_id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `NOT NULL` | Primary key |

There is no invented `source_customer_id` and no unapproved mutable customer
attribute in Milestone 2.

### `product_categories`

Classifies products using a stable category code and display name.

| Column | Type | Nullability | Key and constraints |
| --- | --- | --- | --- |
| `product_category_id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `NOT NULL` | Primary key |
| `category_code` | `VARCHAR(50)` | `NOT NULL` | Unique; non-blank |
| `category_name` | `VARCHAR(200)` | `NOT NULL` | Non-blank |

### `products`

Defines the product catalog, category membership, and optional catalog monetary
attributes.

| Column | Type | Nullability | Key and constraints |
| --- | --- | --- | --- |
| `product_id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `NOT NULL` | Primary key |
| `sku` | `VARCHAR(100)` | `NOT NULL` | Unique; non-blank |
| `product_name` | `VARCHAR(255)` | `NOT NULL` | Non-blank |
| `product_category_id` | `BIGINT` | `NOT NULL` | Foreign key to `product_categories(product_category_id)` |
| `list_price` | `NUMERIC(18,2)` | `NULL` | Non-negative when present |
| `unit_cost` | `NUMERIC(18,2)` | `NULL` | Non-negative when present |
| `currency_code` | `CHAR(3)` | `NULL` | Three uppercase letters when present |

`currency_code` is present if and only if at least one of `list_price` and
`unit_cost` is present. `products.list_price` is the catalog or product price;
`order_items.unit_price` is the transaction price. Equality between them is not
enforced. No foreign-exchange, margin, price-history, or effective-date logic is
introduced.

### `orders`

Records the order event, its channel, optional store and customer context,
transaction currency, and optional order amount.

| Column | Type | Nullability | Key and constraints |
| --- | --- | --- | --- |
| `order_id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `NOT NULL` | Primary key |
| `sales_channel_id` | `BIGINT` | `NOT NULL` | Foreign key to `sales_channels(sales_channel_id)` |
| `store_id` | `BIGINT` | `NULL` | Foreign key to `stores(store_id)` |
| `customer_id` | `BIGINT` | `NULL` | Foreign key to `customers(customer_id)` |
| `order_timestamp` | `TIMESTAMPTZ` | `NOT NULL` | Business-event timestamp |
| `currency_code` | `CHAR(3)` | `NOT NULL` | Three uppercase letters |
| `order_amount` | `NUMERIC(18,2)` | `NULL` | Non-negative when present |

There is no invented `source_order_id`. Store is optional for e-commerce, and
customer is optional for anonymous transactions.

### `order_items`

Records ordered product lines and their transaction monetary values.

| Column | Type | Nullability | Key and constraints |
| --- | --- | --- | --- |
| `order_item_id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `NOT NULL` | Primary key |
| `order_id` | `BIGINT` | `NOT NULL` | Foreign key to `orders(order_id)`; part of unique line identity |
| `line_number` | `INTEGER` | `NOT NULL` | Positive; unique with `order_id` |
| `product_id` | `BIGINT` | `NOT NULL` | Foreign key to `products(product_id)` |
| `quantity` | `INTEGER` | `NOT NULL` | Positive |
| `unit_price` | `NUMERIC(18,2)` | `NOT NULL` | Non-negative |
| `discount_amount` | `NUMERIC(18,2)` | `NULL` | Non-negative when present |
| `line_amount` | `NUMERIC(18,2)` | `NOT NULL` | Non-negative |

The table has `UNIQUE (order_id, line_number)`. Monetary values inherit the
parent order's currency. The database does not enforce a line-calculation
formula.

### `payments`

Records payment events and amounts against an order.

| Column | Type | Nullability | Key and constraints |
| --- | --- | --- | --- |
| `payment_id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `NOT NULL` | Primary key |
| `order_id` | `BIGINT` | `NOT NULL` | Foreign key to `orders(order_id)` |
| `payment_timestamp` | `TIMESTAMPTZ` | `NOT NULL` | Business-event timestamp |
| `payment_status` | `VARCHAR(50)` | `NOT NULL` | Non-blank |
| `payment_amount` | `NUMERIC(18,2)` | `NOT NULL` | Non-negative |

There is no `source_payment_id` and no payment currency column. Payment amounts
inherit the order currency. An order has zero or many payments.

### `returns`

Records return events and quantities against individual order items.

| Column | Type | Nullability | Key and constraints |
| --- | --- | --- | --- |
| `return_id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `NOT NULL` | Primary key |
| `order_item_id` | `BIGINT` | `NOT NULL` | Foreign key to `order_items(order_item_id)` |
| `return_timestamp` | `TIMESTAMPTZ` | `NOT NULL` | Business-event timestamp |
| `return_quantity` | `INTEGER` | `NOT NULL` | Positive |
| `return_amount` | `NUMERIC(18,2)` | `NULL` | Non-negative when present |
| `return_reason` | `VARCHAR(255)` | `NULL` | Non-blank when present |

There is no `source_return_id` and no return currency column. Return amounts
inherit order currency through the order item. An order item has zero or many
returns. Cumulative-return trigger logic is deliberately omitted.

## Indexes

The approved indexes are:

- `orders(order_timestamp)`;
- `orders(customer_id)`;
- `orders(store_id, order_timestamp)`;
- `order_items(product_id)`;
- `payments(order_id)`;
- `returns(order_item_id)`.

## Deterministic reference data

The exact `sales_channels` reference data is:

| `sales_channel_code` | `sales_channel_name` |
| --- | --- |
| `ECOMMERCE` | `E-Commerce` |
| `RETAIL` | `Retail` |

Seed execution follows these semantics:

- a missing expected record is inserted;
- an exact existing code-and-name pair causes no mutation;
- an existing code with a conflicting name causes failure;
- conflicts are never silently overwritten.

## Migration architecture

Repository 1 uses SQL-first, ordered, versioned migrations. The conceptual
sequence is V001 migration metadata, V002 core relational schema, and V003
approved indexes. Migration provenance and SHA-256 integrity are validated, as
is physical schema drift. Accepted migrations are immutable.

Migration-state idempotency means confirming an exact current valid state or
advancing an exact valid older state through missing approved migrations. It
does not mean masking incompatible state or drift.

## Python boundary

Python may support only infrastructure concerns:

- connection establishment;
- migration discovery and ordering;
- checksums;
- migration execution;
- migration metadata validation;
- reference-data execution;
- schema validation;
- centralized logging and error handling.

The architecture explicitly excludes ORM-first schema ownership, Alembic,
repository or DAO abstractions, persistence services, source ingestion,
CSV/JSON readers, Pandas loading or transformation, business-data upserts,
deduplication logic, staging processing, ETL transformations, orchestration,
monitoring, reporting tables, and Azure, Spark, Databricks, Snowflake, or Power
BI functionality.

## Testing expectations

Architecture-level validation must cover:

- real PostgreSQL integration;
- migration integrity;
- physical schema drift detection;
- constraint behavior;
- optional relationships;
- reference-data replay and conflict behavior;
- preservation of Milestone 1 regressions.
